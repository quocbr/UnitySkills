# Unity C# review checks

Use these checks for a requested code review or a focused review after a C# change. They supplement the [C# workflow](workflows.md#c-implementation-and-code-review); they are guidance, not a REST skill or an automatic failure gate. The [Quick Question best-practice skill](https://github.com/tykisgod/quick-question/blob/main/skills/best-practice/SKILL.md) inspired the focused scope and first-pass scanning approach. The rules below are adapted for different Unity versions and project conventions.

## Scope and evidence

1. Follow the user's file or feature scope. Otherwise inspect the `.cs` files changed for the task and the callers, tests, scenes, prefabs, assets, and assembly definitions needed to understand them. An uncommitted diff can help find changed files, but it does not include every relevant caller or serialized reference.
2. Treat a text or script match as a **candidate**, then read its call path and lifecycle. Report a finding only when the condition, consequence, and affected location are supported by evidence. Do not assign High severity merely because a pattern appears in this table.
3. For performance findings, estimate call frequency and scale, then use Profiler data from a development build on the target platform when the impact is uncertain. Editor-only GC samples are not proof of Player allocations: Unity documents that `GetComponent` allocates in the Editor but not in a built project. [Unity GC overview](https://docs.unity3d.com/2023.1/Documentation/Manual/performance-garbage-collector.html).

The generated [scripting](nice-wolf-studio/unity-scripting/GUIDE.md) and [performance](nice-wolf-studio/unity-performance/GUIDE.md) examples use short anti-pattern descriptions. Apply the version and evidence checks here before turning their `GetComponent` or tag-comparison examples into review findings.

## Checks to apply when relevant

| Candidate | Investigate before reporting |
| --- | --- |
| `FindObjectOfType`, `FindObjectsOfType`, or other object searches | Check whether the search runs repeatedly, whether the object can change, and the project's Unity version. The former APIs are obsolete in Unity 6; an explicit reference or version-appropriate `FindFirstObjectByType`, `FindAnyObjectByType`, or `FindObjectsByType` may fit. A singleton is only suitable when its ownership is already established. [Unity API](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Object.FindObjectOfType.html). |
| `GetComponent` in `Update`, `FixedUpdate`, collision callbacks, or loops | Check frequency, target object, and whether caching would remain correct if components can change. Repeated lookup may cost CPU; do not claim it creates Player GC without measurement. [Unity GC overview](https://docs.unity3d.com/2023.1/Documentation/Manual/performance-garbage-collector.html). |
| Collections, LINQ, closures, or string construction in a repeated path | Check whether the expression actually allocates, how often it runs, and whether the allocation matters at the target scale. Prefer reuse or event-driven updates for a measured hot path. [Unity GC practices](https://docs.unity3d.com/2022.3/Documentation/Manual/performance-garbage-collection-best-practices.html). |
| Coroutine or async work with no visible cleanup | Identify who starts it and what ends its lifetime. Deactivating a GameObject or destroying its component stops attached coroutines; setting `MonoBehaviour.enabled = false` does not. Independent tasks, pooled objects, and async continuations need their own cancellation or ownership check. [Unity coroutines](https://docs.unity3d.com/2022.3/Documentation/Manual/Coroutines.html). |
| Event subscription without a nearby unsubscription | Trace the publisher and subscriber lifetimes and look for a matching removal or disposable owner. `OnEnable`/`OnDisable` is useful for activation-scoped subscriptions; other matched lifetime pairs can also be correct. Check for double firing or retained subscribers before claiming a leak. |
| `GetComponent<T>()` dependency without `[RequireComponent]` | Check that `T` must exist on the same GameObject and is dereferenced without a valid fallback. The attribute helps when a component is added, but does not repair already configured GameObjects; inspect those assets too. [Unity RequireComponent](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/RequireComponent.html). |
| Shared state read in `Awake` or `Start` | Identify which object initializes the state and when. Unity does not guarantee the order of `Awake` across GameObjects, while `Start` follows scene `Awake` calls. Report an ordering bug only for a real dependency whose value can still be unavailable. [Unity Awake](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/MonoBehaviour.Awake.html). |
| Public fields, serialized field renames, or new namespaces | Check whether a field is a deliberate API, an Inspector setting, or referenced by scenes and prefabs. Preserve serialized data and callers when refactoring. Check actual `.asmdef` references and platform boundaries; a `using` directive alone does not establish an assembly dependency. |
| `gameObject.tag == ...` or `SendMessage` | `CompareTag` and typed calls are often clearer, especially in repeated paths. Check the actual behavior and cost before asserting allocation or assigning severity. A string-based call that can silently miss its receiver deserves closer review. [Unity CompareTag](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Component.CompareTag.html). |
| Null handling around `UnityEngine.Object` | Check destruction and missing-reference states. Unity objects have special `== null` behavior; `?.` and `??` do not use it. Do not remove guards merely to reduce their number. [Unity Object](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Object.html). |

Documentation comments, naming, namespace style, and field visibility are project conventions unless they cause a concrete defect or violate an explicit project rule. Changes to UI or other unrelated systems are a scope issue, not an automatic C# defect. Keep these observations separate from runtime and correctness findings.

## Report findings

For each finding, give the file and line, the failing call path or state, the consequence, and the evidence or reproduction. Suggest the smallest fix and a way to verify it. Mark a candidate as unverified when the scene, runtime, build, or profiling data needed to establish it is unavailable. A clean scan means only that these checks found no supported issue in the inspected scope.
